
# Purchase Management

## 프로젝트 소개

> 프로젝트 목적

이 프로젝트는 마이크로서비스 아키텍처(Microservices Architecture)를 기반으로 설계되었습니다.  
상품에 대한 정보의 정합성을 추구하며,  
대규모 요청을 처리하는 것을 목표로 하는 프로젝트 입니다.

<br>

> 사용기술
>- 프로그래밍 언어 : **JAVA 21**
>- 빌드 도구 : **gradle 8.11.1**
>- 프레임워크 : **SpringBoot 3.2.0**
>- 보안 : **Security 6.1.0, JJWT 0.11.5**
>- 데이터베이스 : **MySql 8.0**
>- ORM : **Spring Data JPA 3.1.0**
>
>> 분산 시스템 및 서비스 관리
>>- 서비스 관리: **Spring Cloud 2023.0.0 (Spring Cloud Gateway 포함)**
>>- 캐싱 : **Redis**
>>- 메세지 발행 : **Kafka 3.5.1**
>
>> 배포 및 운영
>>- CI/CD : **Docker, Docker-compose**
>
>> 테스트 및 모니터링  
>>- 모니터링 : Prometheus, Grafana
>>- Api-test : PostMan, K6, python

> 각 서비스 주요 기능

**api-gateway** 
- API 요청 라우팅 및 JWT 토큰 검증

- 들어온 각 요청들을 비동기적으로 각 서비스에 요청

**user-service** : 
- 사용자 인증 및 JWT 생성 / 반환
- 사용자 로그인 정보 캐시 저장

**product-service**
- 상품 최초 색인시 내부 서비스에서 필요한 정보 캐시 저장
- 상품이 이미 캐시에 저장되어 있을시, 캐시에서 갯수 반환

**order-service** : 주문 생성 및 관리
- 상품 주문시 캐시에서 상품 리스트의 각 상품 갯수 확인 및 감소
- 상품 갯수 확인중 특정 상품의 갯수가 부족할 경우, 
  해당 상품 리스트에서 이미 감소시킨 상품들의 갯수 복구.

## 성능개선
**일괄 실행환경**
- cpu : 2~2.5개
- memory : 4G 고정
- k6, 1000vus로 10만개 요청

**개선 요소** 
1. 하나의 시퀀스 내에서 여러 개의 DB 트랜잭션 발생
해결 : @Transactional 어노테이션으로 다수의 각 트랜잭션을 하나의 트랜잭션으로 처리하여 커밋 비용 절감.

2. 수백개 이하의 소량의 데이터를 API 스트림으로 처리하여 효율이 저하.
해결 : 소량의 데이터를 다룰 것으로 예상되는 List의 처리를 For문으로 처리.

3. 개발단계에서 사용한 현재 필요없는 표준 출력들의 쓸데없는 메모리 차지.
해결 : 필요없는 표준 출력들을 삭제.

**개선 결과**
- 평균 요청 시간 약 36.49% 감소( 1.88s)
- 초당 처리 갯수 약 45.32% 증가()
- 평균 요청 시간 : 2.96s => `1.88s`
- 초당 처리 갯수 : 약 287.1개 =>`약 417.2개`

## 트러블슈팅
### 1. 데이터 캐싱으로 생기는 문제
**문제점** 
- 캐싱된 데이터의 원본(DB)을 kafka 메세지로 제어함에 따라, 
캐싱된 데이터와 원본 데이터의 시간상 간극 확인.
해당 간극이 있는 상태로 서비스가 비정상 종료되면 데이터가 소실됨. 

**해결** 
- Kafka 메세지를 데이터를 추적 가능한 정보와 함께 발송, 
문제가 생기더라도 복구 가능하도록 함.

### 2. 비관적 락 사용으로 생기는 문제
**문제점**
- 비관적 락 사용시 성능이 저하되며,  요청이 멈추는 일이 생김

**해결**
- 락을 거는 시점을 해당 시퀀스에서 가능한 최후미에 위치시켜 기능저하 감소.
특정 테이블에 대한 락을 거는 명확한 순서를 지정하여
서로 다른 시퀀스틀끼리 락이 교차되어 교착상태에 빠지는 것을 예방함과 동시에, 
 락 획득을 위해 대기하는 최대 시간을 설정하여 교착상태가 해제될 수 있게 함
